# Games

The **Games** page (`/games`, after Music) connects Minecraft to Tokio, Bedrock Edition by itself and Java Edition through the Tokio mod (`../tokio-minecraft-mod`, see "Minecraft mod repo" in `AGENTS.md`). Users make game actions: an Alerts-style trigger plus steps that run Minecraft commands, each action for one edition. The mod is published as `tokio-app/minecraft-mod` (v0.1.0, `https://github.com/tokio-app/minecraft-mod/releases/latest`); the Games page links to its install steps on the website (`MINECRAFT_MOD_DOCS_URL`).

## Connection

- `MinecraftConnection` (`services/games/minecraft.ts`) is a `ws` server on `MINECRAFT_PORT` (37892, `NOTE: DO NOT CHANGE`, players type it), for both editions.
  - **Bedrock** connects with `/connect <this PC's address>:37892` from its chat, in a world with cheats on, after **Settings → General → Network settings → Enable WebSockets**.
  - **Java** connects with `/tokio connect <address>:37892` (`/tokio connect` alone is `localhost:37892`), from the Tokio mod: Fabric, Minecraft 26.3, single-player and LAN worlds the player hosts, no cheats (the mod runs commands as the host at command-block permission, and their feedback isn't shown in chat). The mod offers the subprotocol `MINECRAFT_JAVA_PROTOCOL` (`tokio.java.v1`, `NOTE: DO NOT CHANGE`); `handleProtocols` selects it when offered, otherwise the first offered (Bedrock's `wsencrypt`), and `socket.protocol` tells the edition. The mod never reconnects by itself and tells the player why a connection ended (Tokio's close reason).
  - The server has no host, so one command per address (`GET_NETWORK_ADDRESSES`) works from this PC and from another device; the page shows `localhost` only when the PC has no address.
- It listens only while `settings.games.minecraft.enabled` is on (off by default). `GamesService`'s constructor opens nothing; `configure` (startup and `SET_GAMES_SETTINGS`) turns it on or off.
- `verifyClient` refuses any upgrade with an `Origin` header: browsers always send one, the game never does, so web pages can't take the socket. This is the exception to "no Origin checks" on the overlay server.
- With **Require Encrypted WebSockets** on (the game's default) Bedrock offers the subprotocol `com.microsoft.minecraft.wsencrypt`. `ws` echoes it back; keep that.
- One game at a time: a new one, of either edition, replaces the old one, which is closed with 4000 "Another game connected to Tokio.". Turning Minecraft off closes it with 1001 "Minecraft was turned off in Tokio.". The Java mod shows those reasons in chat. `maxPayload` is 64 KiB. The server and each socket handle `error` (a bad frame would throw in main).

## Protocol

The Java mod's side is `../tokio-minecraft-mod/PROTOCOL.md`: change both together. Java skips Bedrock's encryption: no handshake, the game counts as connected as soon as the socket opens, and the same `commandRequest` / `commandResponse` frames go as plain text (`statusCode` 0 is ok, -1 failed). The mod reads only `header.requestId` and `body.commandLine` of a request, answers a Bedrock `enableencryption` line with -1 ("Update Tokio to use the Java mod."), and fails a command while the host isn't in the world. The rest of this section is Bedrock's.

- Tokio sends a `commandRequest` (header `version: 1`, a `requestId`) with `enableencryption "<publicKey>" "<salt>" cfb`: ECDH `secp384r1`, public keys as base64 SPKI DER (`SPKI_PREFIX` plus the raw point), a 16-byte salt, key = SHA-256(salt + secret), IV = key[0..16].
- The game answers in three frames: `ws:encrypt` (text, with `publicKey`), a text `commandResponse` with `publicKey`, then an encrypted binary `commandResponse` `{ statusCode: 0 }`. Set the keys in the message handler, never after an `await`: the third frame can arrive in the same chunk, and a missed frame desyncs the stream for good.
- After that, binary frames are encrypted and text frames plain, both ways. "Too many commands" errors come as plain text even after the handshake.
- The mode is `aes-256-cfb`, not `cfb8`: Electron's BoringSSL has no `aes-256-cfb8`, while Node's OpenSSL (Vitest) does, so only Electron itself proves the handshake.
- No answer within `handshakeMs` (5 s) means the player turned encryption off: commands go as plain text.
- Commands: body `version: 42` (1 fails on `execute … run`), `commandLine`, `origin: { type: "player" }`. They run as the connected player, so `~` is where they stand. A reply is a `commandResponse` or an `error`; `statusCode >= 0` is ok. Replies are in the game's language (`statusMessage`, or `message`, or nothing).
- Limits: the game allows 100 commands in flight; Tokio keeps 50 (`MAX_IN_FLIGHT`) and 10,000 waiting (`MAX_WAITING`), and fails the rest. `MAX_WAITING` is only a safety net: `GamesService` paces each action's runs. A command with no answer fails after `timeoutMs` (10 s). A game that leaves fails every pending command with "Minecraft disconnected."

## Statuses

`GameStatus` is `off` (disabled), `waiting` (listening with no game, also after the game leaves and during Bedrock's handshake), `connected` (after Bedrock's handshake, or as soon as Java joins; carries `edition`, `"bedrock"` or `"java"`) or `error` (`error` is text for the user, like "Port 37892 is in use."). `GamesService.onStatus` pushes `GAMES` (`app:games:res:games`) with the settings and `{ minecraft: status }` on every change. A failed listen at startup keeps the setting on and warns once (`GAME_LISTEN_FAILED`); the page shows the status.

## Actions and commands

- `Profile.games.actions` holds `GameActionSchema` (`id`, `enabled`, `edition`, `trigger`, `steps`); `edition` defaults to `"bedrock"`, so actions saved before Java are Bedrock's; the trigger is `TriggerSchema`, shared with alerts. `settings.games` (the connections' switches) is in the store, the same for every profile; the actions belong to the profile.
- `gameCommands(step, fill, edition)` (`commands.ts`) turns a step into commands, spawn times `amount`:
  - Bedrock: `summon <mob>[ "<name>"] ~ ~ ~`, `give @p <item> <n>`;
  - Java: `summon minecraft:<mob> ~ ~ ~[ {CustomName:"<name>"}]`, `give @s minecraft:<item> <n>`;
  - both: `weather <w>`, `time set <t>`, and the command step's template, one leading `/` dropped.
  - Hazard steps (`GAME_HAZARDS`, named by `HAZARD_NAMES`) are built-in ways to try to kill or prank the player, each with fixed commands per edition in `hazardCommands`, checked against Java 26.3's command tree and registries and Bedrock's `mojang-commands.json` (bedrock-samples): falling TNT (10 blocks up) and a TNT ring (8 around, 3 blocks out), a lightning bolt, a charged creeper (Bedrock's `minecraft:become_charged` spawn event, Java's `powered`), evoker fangs (Bedrock's `evocation_fang`), an anvil drop, harming (instant damage II), a launch alone or after a water bucket (`launch_water`), freeze (slowness 255), lights out (darkness) and dizzy (nausea), each for its `duration` (1–120 s, default 10), turn around (`teleport` with `~180`) and a random teleport (`spreadplayers` within `distance`, 10–10,000 blocks, default 1,000). They carry no NBT but the creeper's and the fuse. The creeper's hiss was one before release: `GameStepsSchema` drops its saved steps, since a Default profile that fails to load is written over.
    - **Fuse** (the TNT's, seconds, default 4): Java's `fuse` in ticks. Bedrock's TNT can't take one: it burns 4 s, or 0.5–2 s at random with its `from_explosion` event, used at 2 s or less; the page says which next to the field on Bedrock actions.
    - **Launch** (`height` 5–300 blocks, default 50; `seconds` 1–10, default 1): `launchPlan(height, seconds)` plays Java's physics (speed eases toward 0.05 × level by a fifth a tick, 2% drag, then gravity 0.08 after the push) for the weakest levitation level that gets there within `seconds`, up to 256 (`MAX_LEVEL`, amplifier 255, the command's most; Java 26.3 sends it as a VarInt), and when to stop. Its commands are the effect, a `{ wait }` and `teleport ~ ~ ~`, which zeroes the climb's speed in Java 26.3 (`TeleportCommand` sends no `DELTA` relatives), so the fall starts at the top instead of drifting up on momentum. The stop is never before the push ends, which would lift the player again; past level 256's reach (about 190 blocks in 1 s) the climb goes on on momentum and stops when it gets there (300 blocks in 1 s stops at 1.6 s). Bedrock's levitation may differ.
    - **Waits:** `gameCommands` returns `GameCommand`s, a command or `{ wait: ms }`. `GamesService._send` sends the commands up to a wait at once, then waits for their answers and the time before the rest, so a launch holds its action's next run, and Test, until it stops. A wait has no result.
    - **Anvil:** `setblock ~ ~20 ~ anvil keep`, because Bedrock can't summon a falling block: it never replaces a block, fails when there's no room, and the anvil stays in the world. Java 26.3 schedules a setblock'd anvil's fall unless the mode is `strict`.
    - **Help steps** (`GAME_HELPS`, named by `HELP_NAMES`) are the other side, `helpCommands`: netherite armor, put on at once over whatever the player wears, which is lost (the user's call): Java's `item replace entity @s armor.<slot> with`, Bedrock's `replaceitem entity @p slot.armor.<slot> 0`. Only `replace` works: the Java mod counts an `execute if` that runs nothing as failed, and Bedrock can't tell an empty slot. The other armor sets were helps before release; `GameStepsSchema` makes their saved steps netherite, a full heal (instant health V and saturation XX for 1 s) and potion effects for `duration` (1–600 s, default 30), at the levels in `HELP_EFFECTS`. Every id is in both editions' lists, Java 26.3's registries and Bedrock's command enums.
    - Only `REPEATED_HAZARDS` (lightning, charged creeper, evoker fangs) repeat by the amount, and only they show it; the rest run once (the user's call for TNT).
  - Amounts are 1–100. A mob or item id that isn't `/^[a-z0-9_]+$/` runs nothing.
- Variables are `ALERT_MESSAGE_VARIABLES` per trigger, filled by `formatAlertMessage(text, payload, commandValue)`. `commandValue` strips `" ' \ { } [ ] § @` and control characters, collapses whitespace and caps at 100 characters, so a nickname can't inject NBT or selectors. A spawn name goes through it whole, then `JSON.stringify`. The command template is the user's own and isn't escaped.
- `GamesService.handle` (called from `registerConnectorEvents` next to the alerts, whatever features are on) returns when Minecraft is off or in error. It runs its own `GiftStreaks` once per event; `{count}` is the streak's total. An action on **Every gift** runs once per gift added, and a Like action once every `likes_every` likes (default 100) from all viewers, counted per action in `_likes` with the rest carried over, as the countdown timer counts them; gifts and likes are never capped (the user's call: every gift and like count runs). Each action has a FIFO backlog (`_backlogs`) of batches (one run's filled commands, `times` left) that `_pump` serves: one run's commands at once, then `RUN_GAP_MS` (100 ms) after their answers before the next run, so a lone run goes out at once and actions pump side by side. An action on any other trigger takes no new runs while its backlog holds `MAX_BACKLOG` (100, the `times` left of every batch, the one being sent included): `_queue` reports `full` and resolves the skipped batch at once. Before each run, the action missing, disabled or of another edition in the latest `games` given to `handle`, or Minecraft off, drops the rest quietly (filled commands stay as they were accepted); no game of its edition reports `offline` once and drops it, as does a run that failed because the game left. `handle` resolves once its own batches are served or dropped; `dispatchGames` isn't awaited, so a backlog never holds up other events. Matching is `matchesTrigger` and `giftOf` in `src/main/helper/triggers.ts`, shared with `AlertsService` (see `.claude/rules/alerts.md`). `DISCONNECTED` calls `clear`, which forgets the streaks and the likes counted, not the backlogs.
- An action runs only while a game of its edition is connected (`GamesService._unreachable`): `handle` and `test` use the action's `edition`, and a game of the other edition counts as not connected.
- **Test** (`TEST_GAME_ACTION`, `notify: false`; the request carries `edition`) runs the steps once with `generateTikTokEventSample` (Emote uses Chat) and returns each command with the game's reply. It fails with "Turn on Minecraft and connect the game first." with no game, and "Connect Minecraft Java Edition first." (or Bedrock) when the other edition is connected. Its reply carries the action's `id`, failures included; the page ignores other ids.

## Notices and logs

- Logs go to `games.log` (`Files.logs.games`); the feedback source is `games`. A status change is logged once, never per command.
- `registerGames` (`src/main/events/init.ts`) turns `GamesService.onError` into notices, and logs only when the notice goes out:
  - `GAME_NOT_CONNECTED`, key `game:minecraft:offline`, 60 s: an action ran while the toggle is on and no game of its edition is connected. It names the edition: "Minecraft Java Edition isn't connected, so the X action didn't run. Type the /tokio connect command from Games in the game's chat." (Bedrock's says `/connect`);
  - `GAME_COMMAND_FAILED`, key `game:<action id>`, 30 s (`REPEAT_NOTICE_MS`): the game refused a command, with its reply;
  - `GAME_BACKLOG_FULL`, key `game:<action id>:full`, 30 s: an action had `MAX_BACKLOG` runs waiting, so an event's were skipped. "The X action has 100 runs waiting, so new ones are skipped until Minecraft catches up."
- `GAME_ACTION_FAILED` reports an unexpected throw from `dispatchGames`. The toggle, the actions' autosave and Test send no success notices.

## Renderer

- `pages/Games`: `MinecraftSection` (toggle, status, then, until a game connects, the setup of both editions side by side: each edition's steps and a command per address of this PC, `connectCommand(host, edition)`, with copy buttons titled "Copy the Bedrock command" / "Copy the Java command" and a caret that blinks while waiting on each first one; the Java steps link to `MINECRAFT_MOD_DOCS_URL`, the website's `#java-edition` anchor, so keep that heading there) and `ActionsSection`. The status reads "Connected to Java Edition" or "Bedrock Edition" (`statusText`). `TriggerFilter` comes from `components/AlertItem`, and the trigger picker offers `GAME_TRIGGERS` (`helper.ts`): `TRIGGER_OPTIONS` without Super Fan Join, Member Join, Envelope, Super Fan Box and Music Change (the user's call). The schema still takes them, so an action saved with one keeps running, its picker empty until another is picked. Gifts and emotes load as on Alerts. Like shows its own "every N likes" field (`likes_every`) in the filter's place. `TriggerFilter` renders nothing for triggers without a filter. The trigger's `min_coins` and `roles` (the Alerts editor's conditions) aren't offered here; actions keep their defaults, which match everything.
- An action's header has an **Edition** picker (`EDITIONS`) before its trigger, and a **Duplicate** button next to Test and Remove: the copy gets a new id and goes right after the original. A new action takes the connected game's edition, else Bedrock (`Games/index.tsx`).
- `MOBS[edition]` and `ITEMS[edition]` (`helper.ts`) come from `src/common/games/minecraft-bedrock.json` and `minecraft-java.json` (`MINECRAFT_NAMES`, in common so main can name the overlay's rows), id → English name, sorted by name. `withEdition(action, edition)` moves an action's mobs and items to the other edition's ids (`idIn`): the same id, else `PAIRS` (ids that differ and whose names differ too: `ender_crystal`/`end_crystal`, the zombie pigman spawn egg, silver glazed terracotta, `undyed_shulker_box`/`shulker_box`), else the id with the same English name (Bedrock's `web` is Java's `cobweb`), else a zombie or a diamond. Add a pair when a regenerated list has an id no name matches. To regenerate the Bedrock list after a game update:
  - **Ids:** Mojang's `bedrock-samples` metadata: `metadata/vanilladata_modules/mojang-entities.json` and `mojang-items.json`, kept to the values of the `EntityType` and `Item` enums in `metadata/command_modules/mojang-commands.json` (what `summon` and `give` take).
  - **Left out:**
    - mobs: projectiles, boats and minecarts, the armor stand, `npc` and `cushion`;
    - items: command, structure, barrier, jigsaw and light blocks, and Education's `allow`, `deny` and `border_block`.
  - **Names:** the game's `en_US.lang`: `entity.<id>.name`, the item's `serialization_id`, `item.<id>.name` or `tile.<id>.name`, otherwise the id in title case. `tnt` is "Primed TNT".
  - **Check:** run every id in the game, with `testfor @e[type=<id>]` and `clear @p <id> 0 0`, which count without changing the world. An unknown id is a syntax error. The current list is 1.26.50, all 1,689 known.
  - **Java's ids differ for some:** Bedrock has `web` (Cobweb), `evocation_illager` (Evoker) and `zombie_pigman` (Zombified Piglin); `withEdition` maps them by name.
- To regenerate `minecraft-java.json` (the current list is 26.3: 95 mobs, 1,645 items), from Mojang's own data, with JDK 25:
  - **Ids:** download the version's server jar (`downloads.server.url` in its version JSON) and run `java -DbundlerMainClass=net.minecraft.data.Main -jar server.jar --reports --output generated` (in PowerShell quote the `-D…` argument). Read `generated/reports/registries.json`: `minecraft:entity_type` and `minecraft:item`.
  - **Names:** `assets/minecraft/lang/en_us.json` from the client jar: `entity.minecraft.<id>`, and for items `item.minecraft.<id>.new`, `item.minecraft.<id>` or `block.minecraft.<id>`. So no two items share a name, music discs are "Music Disc <song>" (from `item.minecraft.<id>.desc`, the part after " - ", capitalized), armor trims come from `trim_pattern.minecraft.<pattern>` and upgrades from `upgrade.minecraft.<id>`.
  - **Left out:** the same kinds as Bedrock's list: player, projectiles, boats and rafts, minecarts, armor stand, displays, marker, interaction, `area_effect_cloud`, `item`, `falling_block`, `leash_knot`, painting, item frames, `evoker_fangs`, `ominous_item_spawner`, `cushion`, `mannequin`; items: `air`, command blocks and their minecart, structure blocks and void, jigsaw, barrier, light, `debug_stick`, `test_block`, `test_instance_block`. Kept: `tnt` ("Primed TNT"), `lightning_bolt`, `end_crystal`, `firework_rocket`, `experience_orb`.
- Actions save through `useEditableSettings("games")`; the toggle emits `SET_GAMES_SETTINGS` at once.
- An action's **Test** results fold in a `<details>` under `testSummary` (how many commands ran or failed). It opens with the first results, and later tests keep a fold. The list shows the last 25 (`RESULTS_SHOWN`) of up to 100, so an earlier failure shows only in the summary.

## Overlay and Minecraft pictures

The **Overlay** section after Actions builds the games overlay: each shown action is a row, the event (a gift's or emotes' pictures, Tokio's sprite for follows, shares, likes, chat and Super Fans, or text like "Any gift"), a pixel arrow, then the picture and name the streamer picked. It's served at `MINECRAFT_OVERLAY_PATH` (`NOTE: DO NOT CHANGE`, OBS links use it): `/games/minecraft/` shows every column, `/games/minecraft/<column>/` one (`getMinecraftOverlayURL(column?)`). Every page connects with the id `GAMES_PATH` (`"games"`); later games get their own `/games/<game>/`.

- **Saved data:** per action `GameActionSchema.overlay` (`show`; `image`, a `{ name, file }` from the Minecraft library or `null`; `event`, its text, `""` for the automatic one; `name`; both texts max 40; `column`), and the look in `Profile.games.overlay` (`layout`, `"list"` or `"carousel"` (`GAMES_OVERLAY_LAYOUTS`); `format`, `"arrow"` or `"sticker"` (`GAMES_OVERLAY_FORMATS`); `columns`, 1 to `GAMES_OVERLAY_MAX_COLUMNS` (4); `pictures_only`; `text_below`, the texts under the pictures; `event_size`, `"small"`, `"medium"` or `"large"` (`GAMES_OVERLAY_SIZES`), the event's pictures; `font`; `text_color`; `accent_color`, the lit glow; `arrow_color`, the arrows'). All have defaults, so older profiles load. They save with the actions through `useEditableSettings("games")`.
- **Rows:** `gameOverlayRows(games, { gifts, emotes, mediaURL })` (`src/common/util/games.ts`) is shared by main and the preview, like `timerTriggers`.
  - **Shown:** an action shows when it's enabled, `show` is on, and it has a picture or a name. Rows keep the actions' order.
  - **Event pictures:** every picture of the trigger's gifts (`gameEventPictures`; the gift lists are TikTok's then the custom ones, so TikTok's entry wins) or emotes (`Profile.emotes`), each once. Follow, Share, Like, Chat and Super Fan get Tokio's own pixel art (`EVENT_SPRITES`, `src/common/games/sprites.ts`): 13×13 grids of color letters drawn as SVG `data:` URLs, a path per color and a rectangle per run, `crispEdges`. They're ours, never TikTok's artwork; the heart and the plus are Tokio's rose, Super Fan's crown gold with rose gems (the user's pick over a star). A gift or emote trigger with none picked has no picture. An event with pictures shows only them, on the page, in the preview and in the builder's row, which has no event text field then (the text stays in the page, hidden, for when every picture fails to load). Several take turns in one place, crossfading every 2 s (`ROTATE_MS`): the page turns every slot on one timer, the preview and the rows with `usePictureTurn`. In one at a time, a row's gifts start from the first as its turn begins, and its turn lasts until each has shown: `max(TURN_MS, gifts × ROTATE_MS)`, so 4 s for two (the page's `rotate` and `turnMs`, the preview's `usePictureTurn(currentId)`).
  - **Chat** is the exception: its row has `withText`, so its side never gets `has-picture` and its message shows by its bubble, with **Pictures only** too. Its text is the `event` override, else the keyword quoted (“tnt”), else none (no empty text span). Its builder row keeps the event text field ("No text" as the placeholder without a keyword).
  - **Likes:** `eventCount` (`gameEventCount`, `likes_every` over 1) shows on the heart's corner with the same `games-count` as the Minecraft side, and in the builder's row.
  - **Event text:** the `event` override, else `gameEventText`: the gift names joined with " or " ("Any gift" with none picked), "100 likes" (`likes_every`), chat's “keyword” ("" without one), else `ALERT_TRIGGER_LABELS`. It names the pictures for screen readers in the builder (chat's bubble is "Chat").
  - **Name:** the `name` override, else `gameStepsText`: what the steps make, named by the action's edition (`MINECRAFT_NAMES`, `WEATHER_NAMES`, `TIME_NAMES`, `HAZARD_NAMES`), with counts over 1 (only for `REPEATED_HAZARDS`) ("Zombie ×5, Thunder"); commands and ids the lists don't have name nothing. The builder shows it as the name field's placeholder, as the event's.
  - **Picture:** `mediaURL(file)`: main passes `/games/minecraft/pictures/<encoded file>` (`MINECRAFT_PICTURES_PATH`), the preview `getPicturePreviewURL`.
  - **Count:** with a picture, the amount of the first mob or item over 1 (`gameCount`) shows on the picture's bottom right corner (`games-count`, like an inventory's stack, also on the builder's picture button), and the default name leaves it out (`gameStepsText(action, true)`: "Zombie"). Without a picture it stays in the name ("Zombie ×5").
  - **Column:** the action's `column`, the last one when the look has fewer `columns`.
  - Rows carry both texts. **Pictures only** is the look's job: it hides a text next to a picture, and a side without a picture keeps its text.
- **Page:** `ServerService` serves it from memory at `/games/minecraft{/:column}` like `/timer/`, a column only when it's digits (anything else, like the pictures' folder, passes on): `games.html?raw` with Archivo (`__ARCHIVO__`) and the shared stylesheet (`__STYLES__`) inlined. It opens a raw WebSocket with `?id=games`, reconnecting after 2 s, and ignores the live events every client gets. Text goes in with `textContent`, the font with `JSON.stringify`, colors as CSS variables (the schema keeps them hex), and a picture that fails to load is hidden. `--fit` shrinks it until all rows fit. It reads its column from its path and keeps only that column's rows (all of them at `/games/minecraft/`).
- **Pushes** (`src/main/helper/games.ts`):
  - `sendGamesOverlay(services)` sends `tokio:games` `{ look, rows }` to `GAMES_PATH` clients, from the active profile, `overlayService.getGifts()` and `getCustomGifts()`. It logs a failure and never throws, so it can't fail the change that called it.
  - It runs when a games page connects (`serverService.onConnect` in `registerGames`), after `refreshGifts` at startup, after `recordGift` saved a custom gift, after `UPDATE_GAMES_SETTINGS` saved (none after a failed save), after `SET_PROFILE` and after `REMOVE_MINECRAFT_PICTURE`.
  - `sendGamesRun(services, id)` sends `tokio:games:run` `{ id }`, which lights the row for 1.5 s after its last run, so a burst glows steadily. One at a time (3 s turns) jumps to the lit row and holds it.
- **`onRun`:** `GamesService.onRun(listener)` (one listener, set in `registerGames`) is called in `_pump` right before each run's `_send`: once per run, never for an action's **Test** or an offline drop. `TEST_GAMES_OVERLAY { id }` (`notify: false`) sends the same run message from the section's Test, which lights the next shown row in the preview and on stream.
- **Shared stylesheet:** `src/common/games/overlay.css` is the overlay's one look. `ServerService` imports it raw (`?raw`) into the page, and `OverlayPreview` imports it as a plain stylesheet, the only one the renderer loads that way. It loads globally, so every class starts with `games-`, and the page's markup and the preview's (`sections/OverlayPreview.tsx`) must stay in step. Pictures float over the game with a halo that follows their shape, with no box behind them, gifts and Minecraft pictures alike (the user's call: no black backgrounds). A lit row's texts take the accent and its pictures glow along their shape, flashing unless `prefers-reduced-motion`. A Minecraft picture drawn at twice its size or more (a 16×16 icon) gets `games-pixelated` (`image-rendering: pixelated`) from `sharpen` on load and on each fit, in the page and the preview alike. Gifts and smaller scales stay smooth, since Chromium's pixelated is nearest-neighbor when shrinking too. It has to work in OBS 30's Chromium 103: no `:has()`, nesting, subgrid or container queries; the page's script sets classes like `has-picture` instead.
- **Formats:** **Arrow** is the spine above. **Sticker** (`games-sticker`, the user's reference: the gift stuck on the item's corner) drops the arrow: each row is its own grid, its sides `display: contents`, with the action's picture large (3.2em) in a 3.7em square and the event's slot half its size (at Small) on the bottom left corner, over it (`z-index`), the texts beside, the name over the event's text. The square holds the overhang, so `fit` counts it. Without the action's picture (the row lacks `has-result-picture`, which the page and the preview set, and the page clears when that picture fails), the event's takes its place. The row has a fixed height and `minmax(0, 1fr)` rows around the texts: with a plain `1fr`, Chromium sized those rows from the pictures across them and the texts landed off center. With **Text below pictures** (`games-text-below`), Sticker puts the texts under the pictures, everything centered on one line down the column: the action's picture centered, the sticker hanging off its left by a margin, in a column at least 4.2em wide so the overhang counts when fitting. One at a time stacks the row boxes in one cell and fades them, centered. The look panel shows the **Arrow** color only with Arrow. With Arrow, **Text below pictures** makes each side a grid, its picture on a 2.5em line and its text under it (`justify-items` toward the arrow, so a long name doesn't push its picture away); a text with no picture beside it (`:last-child` on the event's side, `:first-child` on the result's, from the markup's order) stays on the pictures' line, and the sides and the arrow align to the top so the arrows stay on that line. Those rules use `:not(.games-sticker)`, as Sticker's sides are `display: contents`.
- **Event picture sizes:** **Event pictures** (Small, Medium, Large) sizes the gifts, emotes and Tokio's sprites, not the action's picture. The page and the preview set `games-event-medium` or `games-event-large` (Small has none), which set `--games-event-scale` (1, 1.25, 1.5), and every size that follows from the event's picture is a `calc` of it: Arrow's slot (2em at Small), its pictures' line with text below (`--games-line`, at least the action's 2.5em) and the arrow's offset on it, and Sticker's sticker (`--games-sticker`, 1.6em at Small), its overhang (`--games-overhang`, 0.5em) and the square (`--games-square`, 3.2em plus the overhang), so a larger sticker hangs further off and the row grows with it. The variables hold `em`s, which resolve where they're used: every element using them has the overlay's font size.
- **Builder layout:** the rows panel is as wide as its rows need (`.overlay`'s `auto` track) and the preview and look take the rest, Layout, Format, Columns and Event pictures side by side (wrapping). The rows share one grid (each `li` a `subgrid`), so arrows line up while the event column is only as wide as its widest content: one picture when every event is a gift, a text field when one isn't.
- **Columns:** with more than one, each row gets a **Column** picker and the section gives one URL per column. `OverlayPreview` draws the columns side by side, each in an equal share of the width, which its overlay shrinks to fit as the page fits its source (`--fit`, written to the style in a layout effect, so measuring doesn't render again).
- **Reserved id:** `CatalogOverlaySchema` refuses `games`, like `alerts` and `timer` (see `.claude/rules/overlays.md`).

### Minecraft pictures library

- Only for Minecraft, shared by all profiles: `settings.minecraftPictures` (`{ name, file }[]`), files in `Folders.minecraftFolder` (`~/.tokio/games/minecraft`; later games get folders beside `minecraft`), named by a hash of their content. png, jpg, jpeg, gif and webp (`IMAGE_EXTENSIONS`, `src/common/util/alerts.ts`) up to `MEDIA_MAX_BYTES`. A rebuilt store recovers the folder with `_findFiles`, named from the actions' `image`s, else "Recovered picture N".
- `GamesService` has `setPicturesFolder`, `importPicture` and `deletePicture`; imports go through `importFile` (`src/main/helper/library.ts`, shared with `AlertsService`).
- **Served:** the overlay server mounts the folder at `/games/minecraft/pictures/` (`MINECRAFT_PICTURES_PATH`, `serverService.mount`, next to `/alerts/media/`); the app's windows load it as `tokio-media:///games/minecraft/<file>` (`getPicturePreviewURL`; `mediaFile` in `helper/preview.ts` serves only images right in that folder).
- **Requests** (`pages/games.ts`):
  - `GET_MINECRAFT_PICTURES` replies `MINECRAFT_PICTURES`.
  - `IMPORT_MINECRAFT_PICTURE { id }` opens a dialog for one or more pictures and adds them all (one bad file doesn't stop the others). It replies `SET_MINECRAFT_PICTURE { id, picture }` with the first, which goes on that action, and `MINECRAFT_PICTURES`. Its notices go out in the handler; the picker shows a failure itself.
  - `REMOVE_MINECRAFT_PICTURE { file }` takes it out of the library, then off every action in every profile (`removeFromGames`, which shares `_updateProfiles` with `removeFromAlerts`), pushes `MINECRAFT_PICTURE_REMOVED { file }` and the overlay, then deletes the file. A profile that can't be saved keeps the file and fails with `saveFailure()`.
- **Renderer:** `PicturePicker` (`pages/Games`) is a `Modal` with a `SearchToggle` and a thumbnail grid (the current one `aria-current`), each with Delete (`DeletePictureModal` in `components/DeleteModals`); its footer has Clear, **Browse files...** and Done. It imports the media picker's CSS. The page applies a `SET_MINECRAFT_PICTURE` reply only to the action that asked (`asked`), and `MINECRAFT_PICTURE_REMOVED` clears the picture from the actions it shows, so the next save doesn't bring it back. `OverlaySection` warns when the overlay server is off (`GET_SETTINGS`).

## Tests

- `minecraft.test.ts` plays the game with a real `ws` client on port 0: it does the client side of Bedrock's handshake (the same `aes-256-cfb`, its three frames corked into one TCP chunk), plays the Java mod too (the `tokio.java.v1` subprotocol, plain frames), answers commands, and covers Origin, a port in use, the limits, drops, and one edition replacing the other. A port in use is made with a listen that has no host (macOS `SO_REUSEADDR`).
